## 商品详情缓存流程

```text
请求商品详情
→ 查询 Redis
→ 命中正常 JSON：直接返回
→ 命中 __NULL__：返回商品不存在
→ Redis 未命中：查询 MySQL
→ MySQL 查到商品：写入 Redis，TTL 10 分钟
→ MySQL 查不到商品：写入 __NULL__，TTL 1 分钟
```

## 三类缓存问题

| 问题 | 含义 | 当前/常见解决方案 |
| --- | --- | --- |
| 缓存穿透 | 请求的数据在数据库中不存在，导致请求每次都穿过缓存访问数据库。 | 空值缓存、参数校验、布隆过滤器 |
| 缓存击穿 | 一个热点商品的缓存过期，大量并发请求同时访问数据库。 | 互斥锁、逻辑过期、热点 Key 永不过期 |
| 缓存雪崩 | 大量缓存 Key 在相近时间过期，或 Redis 整体不可用，导致数据库瞬时承受大量请求。 | 随机 TTL、多级缓存、限流、降级 |

## 秒杀资格校验流程

```text
JWT 拦截器认证
→ CurrentUserContext 获取 userId
→ Redis 固定窗口限流
→ 查询秒杀活动
→ 校验状态、时间、库存
→ 校验商品存在且上架
→ Redis 3 秒重复请求保护
→ 返回秒杀资格信息
```

## 两种 Redis Key 的区别

| Key 前缀 | 作用 | TTL |
| --- | --- | --- |
| `seckill:request:{activityId}:{userId}` | 防止用户连续点击同一场活动 | 3 秒 |
| `seckill:rate-limit:{activityId}:{userId}:{windowId}` | 限制用户参与同一活动的请求频率 | 1 分钟 |

## 当前方案的边界

- `INCR` 与 `EXPIRE` 不是原子操作；Day116 会用 Lua 脚本优化。
- 当前只校验资格，还没有真正扣减库存或创建订单。
- 3 秒请求保护不能替代“最终只能成功下一单”的唯一约束。
- 固定窗口限流存在分钟边界突刺问题：在相邻两个窗口的边界，用户可能在极短时间内发送两倍的允许请求数。
